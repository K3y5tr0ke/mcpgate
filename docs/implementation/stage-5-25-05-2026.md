## 1. What Was Implemented

Sprint 5 adds a tamper-evident, asynchronous audit log pipeline that records every MCP proxy request — including requests blocked by RBAC — with a SHA-256 hash chain for tamper detection, a WAL fallback sink for Postgres outages, a WebSocket admin log stream, and three carry-over items from earlier sprints.

### Core deliverables

- **Async audit log pipeline** (`internal/logging/pipeline.go`) — buffered channel, single writer goroutine, batch flush by size or timer tick, fan-out to WebSocket subscribers.
- **SHA-256 hash chain** (`internal/logging/hashchain.go`) — each entry's hash is `SHA256(prev_hash || JSON(entry))`, computed in the single writer goroutine so ordering is guaranteed without locks.
- **PostgreSQL sink** (`internal/logging/sinks/postgres.go`) — thin wrapper delegating to `AuditLogStore.BatchInsert`.
- **WAL fallback sink** (`internal/logging/sinks/wal.go`) — NDJSON append-only file; replayed to Postgres on a 5-minute background ticker when Postgres recovers.
- **`AuditLogStore`** (`internal/store/postgres/audit_logs.go`) — `BatchInsert`, `Query` (paginated, filtered), `Export` (JSON/CSV streaming), `VerifyHashChain`, `LatestHashChain`.
- **Logging middleware** (`internal/logging/middleware.go`) — pre-parses POST body, stores message in context, wraps `ResponseWriter`, submits entry after handler returns. Wired **before** RBAC so denied requests are also captured.
- **`proxy.context`** (`internal/proxy/context.go`) — typed context key for sharing the parsed `*proxy.Message` between the logging and RBAC middlewares without double-parsing.
- **Admin log API** (`internal/admin/api/logs.go`) — `GET /api/v1/admin/logs` (paginated query), `GET /api/v1/admin/logs/export` (streaming JSON/CSV), `WS GET /api/v1/admin/logs/stream` (live fan-out with server-side filter).
- **E2E test suite** (`tests/e2e/logging_test.go`) — 4 integration tests covering proxy audit entries, RBAC-denied entries, admin API access control, and hash-chain integrity.

### Carry-over items completed

## 3. Configuration Changes

Two new fields were added to `PipelineConfig` in `internal/config/config.go`:

```go
type PipelineConfig struct {
    BufferSize    int           `koanf:"buffer_size"`    // default 10000
    FlushInterval time.Duration `koanf:"flush_interval"` // default 100ms
    BatchSize     int           `koanf:"batch_size"`     // default 500
    WriterCount   int           `koanf:"writer_count"`   // reserved; pipeline uses one writer
    WALPath       string        `koanf:"wal_path"`       // "" = no WAL fallback
    HashChainSeed string        `koanf:"hash_chain_seed"` // prev-hash for the first entry
}
```

**`WALPath`** — when non-empty, a `WALSink` is instantiated in `server.New()`. It is passed as the pipeline's fallback sink and replayed to Postgres every 5 minutes by a background goroutine. An empty string disables the WAL, which is safe for development but not production.

**`HashChainSeed`** — the sentinel `prev_hash` used when computing the hash of the very first audit log entry. At startup, `server.New()` calls `LatestHashChain()`:
- If the table is non-empty, the stored hash of the last row is used (chain continuation).
- If the table is empty (`store.ErrNotFound`), `HashChainSeed` is used.
- If `HashChainSeed` is also empty, the literal string `"genesis"` is used as the final fallback.

The seed matters for tamper detection: `VerifyHashChain` requires the caller to supply the same seed when verifying the first window of entries. Tests use `"test-genesis"` to make this explicit.

## 4. Hash Chain — Design and Implementation

### Algorithm

Each entry's `hash_chain` column stores `hex(SHA256(prev_hash || JSON(entry)))` where `JSON(entry)` is the full entry serialised with two fields zeroed: `HashChain` (circularity) and `ID` (DB-assigned after insert — see §10).

The Go JSON encoding is deterministic for a fixed struct type. Field order in the serialised output follows Go struct declaration order in `store.AuditLogEntry`.

### `HashChain` struct (`internal/logging/hashchain.go`)

```go
type HashChain struct {
    prev string
}

func (hc *HashChain) Next(entry *store.AuditLogEntry) error {
    content, err := marshalWithoutHashChain(entry)
    ...
    combined := hc.prev + string(content)
    sum := sha256.Sum256([]byte(combined))
    entry.HashChain = fmt.Sprintf("%x", sum)
    hc.prev = entry.HashChain
    return nil
}

func marshalWithoutHashChain(entry *store.AuditLogEntry) ([]byte, error) {
    type shadow store.AuditLogEntry // prevents recursion if entry has MarshalJSON
    tmp := shadow(*entry)
    tmp.HashChain = ""
    tmp.ID = 0
    return json.Marshal(tmp)
}
```

The shadow type idiom creates an anonymous alias of `store.AuditLogEntry`. Copying through the shadow strips any custom `MarshalJSON` method on the outer type, preventing infinite recursion. The two zeroed fields are the only ones excluded from the hash payload.

### Single-goroutine invariant

`HashChain` has no synchronisation. This is intentional: the pipeline's writer goroutine is the only caller. Since `Next` advances `hc.prev` after each call, calling it from multiple goroutines would produce a non-deterministic chain. Keeping it single-goroutine means the hash of entry N is always `SHA256(hash[N-1] || JSON(entry[N]))` in the order entries were submitted.

### Verification (`VerifyChain`)

`VerifyChain(entries []AuditLogEntry, prevHash string)` recomputes the chain from `prevHash`, calling `Next` on each entry in order. Because `Next` mutates `entry.HashChain`, the caller's entries are modified. `VerifyHashChain` on the DB store reads a fresh copy from Postgres, so mutation is safe.

## 5. Pipeline — Lifecycle and Batching

### `Pipeline` struct (`internal/logging/pipeline.go`)

```
entries     chan AuditLogEntry    — inbound from handlers (buffered, cfg.BufferSize)
done        chan struct{}         — closed by Drain() to signal shutdown
drain       chan struct{}         — closed by writer when it exits (Drain blocks on this)
subscribers map[string]*subscriber — fan-out channels for WS stream, guarded by subMu
```

### Writer goroutine lifecycle

```
Start(ctx)  →  go writer(ctx)
                 ┌──────────────────────────────────────┐
                 │ ticker := time.NewTicker(FlushInterval) │
                 │                                        │
                 │  select {                              │
                 │    case entry := <-p.entries:          │
                 │      batch = append(batch, entry)      │
                 │      if len(batch) >= BatchSize: flush │
                 │    case <-ticker.C:                    │
                 │      flush()                           │
                 │    case <-p.done:                      │
                 │      drain remaining, flush, return    │
                 │  }                                     │
                 └──────────────────────────────────────┘
Drain()     →  close(p.done) + <-p.drain   (blocks until writer exits)
```

### Flush sequence

```
for each entry in batch:
    entry.Timestamp = entry.Timestamp.UTC().Truncate(time.Microsecond)  // ①
    if entry.Metadata == nil: entry.Metadata = map[string]any{}         // ②

for each entry in batch:
    chain.Next(&entry)   // computes + sets entry.HashChain

primary.Write(ctx, batch)
  → success: fanOut(batch) to subscribers
  → failure: fallback.Write(ctx, batch) if fallback != nil, else drop+count
```

① and ② normalise fields that change across a Postgres round-trip (see §10 for why this is critical).

### Backpressure

`Submit` is non-blocking: if the channel is full, the entry is discarded and `dropped` (an `atomic.Int64`) is incremented. This is a deliberate trade-off — audit logging must not block or slow down the proxy request path.

### Fan-out for WebSocket stream

After a successful primary write, `fanOut` delivers each entry to every registered subscriber channel (cap 256 per subscriber). Slow subscribers are silently skipped (`select default`). `Subscribe` returns a receive-only channel and a cancel function; the cancel function removes the subscriber from the map and closes the channel, which unblocks the `for range ch` loop in `stream`.

### Pipeline started in `New()`, not `Run()`

The original plan called for `pipeline.Start()` inside `Run()`. This was changed (see §11.1) because E2E tests call `srv.Handler()` and drive requests directly without ever calling `Run()`. Moving `Start` into `New()` ensures the pipeline is always running when the server is usable.

`Start` is called with `context.Background()` rather than the lifecycle `bgCtx`. This is deliberate: if `bgCtx` were cancelled first, the writer could exit before `Drain()` is called, leaving entries in the channel un-flushed. Using `context.Background()` means the writer goroutine lives until `Drain()` explicitly closes it.

## 6. Sinks

### `PostgresSink` (`internal/logging/sinks/postgres.go`)

A one-method adapter: `Write(ctx, entries) → store.BatchInsert(ctx, entries)`. No buffering or retry — the pipeline handles both.

### `WALSink` (`internal/logging/sinks/wal.go`)

```go
type WALSink struct {
    path   string
    mu     sync.Mutex
    logger *slog.Logger
}
```

**`Write`** — opens the file in append mode (`os.O_CREATE | os.O_APPEND | os.O_WRONLY`, mode `0600`), encodes each entry as a JSON line via `json.NewEncoder`. A `sync.Mutex` serialises concurrent calls from the pipeline writer and the background replay goroutine.

**`Replay`** — reads all lines with `bufio.Scanner`, unmarshals each into an `AuditLogEntry`, calls `primary.Write`, and on success truncates the file to zero with `os.Truncate`. Malformed lines are skipped with a warning. Truncation is a best-effort operation: if it fails, the file is not re-processed correctly on the next replay (entries would be double-inserted). A TODO for a later sprint is to use an atomic rename pattern (write to `.tmp`, rename on success).

**`HasContent`** — calls `os.Stat` and checks size > 0. Used by the background goroutine to avoid a file open + scan when the WAL is empty.

**Import cycle note**: `logging.Sink` and `sinks.Sink` are identical interfaces defined in two packages. This is intentional — `internal/logging` cannot import `internal/logging/sinks` (cycle) and `sinks` cannot import `logging` (cycle). The `logging.Pipeline` accepts `logging.Sink`, and `sinks.PostgresSink` and `sinks.WALSink` both satisfy `logging.Sink` implicitly because Go interfaces are structural.

## 7. `AuditLogStore` (`internal/store/postgres/audit_logs.go`)

### `BatchInsert`

Constructs a single multi-row `INSERT` statement with positional parameters. Each row uses 20 columns; parameters are indexed `$1..$N` where `N = len(entries) * 20`. The `client_ip` column is `INET` type, so the placeholder uses a `::inet` cast: `$6::inet`. Nullable columns use helper functions:

```go
func nullUUID(id uuid.UUID) any {
    if id == uuid.Nil { return nil }
    return id
}
func nullString(s string) any {
    if s == "" { return nil }
    return s
}
```

`Metadata` (`JSONB`) is marshalled to a `[]byte` JSON string. If `json.Marshal` returns nil (impossible in practice), a fallback `{}` is used to match what Postgres would store by default.

`ID` is a `BIGSERIAL` column not listed in the INSERT column list; Postgres assigns it automatically.

### `Query`

Uses a window function `COUNT(*) OVER()` to return both the matching rows and the total count in a single query pass without a second `COUNT` query. Filter predicates are built dynamically with positional params to avoid SQL injection. The `Search` filter matches `user_email ILIKE $N OR error_message ILIKE $N` using the same parameter index for both predicates.

### `Export`

Streams rows in ascending time order directly to the `io.Writer` (the HTTP response body), keeping memory usage flat for large exports. For CSV, `encoding/csv.Writer.Flush()` is called after the scan loop.

### `VerifyHashChain`

```go
func (s *AuditLogStore) VerifyHashChain(ctx context.Context, from, to time.Time, genesisHash string) (bool, error)
```

1. Queries entries in `[from, to]` sorted `timestamp ASC, id ASC`.
2. Looks up the `hash_chain` of the last row **before** `from`. If found, that becomes `prevHash`; if not found, `prevHash = genesisHash`.
3. Calls `auditVerifyChain(entries, prevHash)`.

The `genesisHash` parameter was added during debugging (see §11.3). Without it, verifying the very first batch of entries in a fresh database always fails because the lookup returns no prior row, so `prevHash` would default to `""`, which does not match the configured seed.

### `auditVerifyChain` (inlined, not imported from `internal/logging`)

The hash-verification logic is duplicated here rather than imported from `internal/logging/hashchain.go`. Importing it would create an import cycle: `internal/store/postgres` → `internal/logging` → `internal/store`. Duplication is the lesser evil; the two copies share the same algorithm and are both covered by tests.

```go
func auditVerifyChain(entries []store.AuditLogEntry, prevHash string) (bool, error) {
    prev := prevHash
    for i := range entries {
        stored := entries[i].HashChain
        type shadow store.AuditLogEntry
        tmp := shadow(entries[i])
        tmp.HashChain = ""
        tmp.ID = 0          // see §10 — BIGSERIAL excluded from hash
        content, _ := json.Marshal(tmp)
        sum := sha256.Sum256([]byte(prev + string(content)))
        computed := fmt.Sprintf("%x", sum)
        if computed != stored { return false, nil }
        prev = computed
    }
    return true, nil
}
```

### `LatestHashChain`

Not part of the `AuditLogStore` interface — it is a concrete method on `*AuditLogStore` called directly from `server.New()` to seed the pipeline's chain tip at startup. Returning `store.ErrNotFound` on an empty table is a deliberate sentinel so `New()` can distinguish "table empty, use seed" from "query failed".

### `scanAuditEntry`

Two normalisation steps were added during debugging (see §10):

```go
// pgx decodes timestamptz with the local timezone; normalise to UTC.
e.Timestamp = e.Timestamp.UTC()

// INET ::text appends the prefix length (e.g. "127.0.0.1/32"); strip it.
if clientIP != nil {
    e.ClientIP = strings.SplitN(*clientIP, "/", 2)[0]
}
```

Both changes ensure that the entry read back from Postgres produces the same JSON as the entry the pipeline hashed before inserting.

## 8. Logging Middleware (`internal/logging/middleware.go`)

### Final implementation

```go
func Middleware(pipeline *Pipeline, serverStore store.ServerStore) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            start := time.Now()
            ww := chimw.NewWrapResponseWriter(w, r.ProtoMajor)

            if r.Method == http.MethodPost && r.Body != nil {
                buf, err := io.ReadAll(r.Body)
                if err == nil {
                    r.Body = io.NopCloser(bytes.NewReader(buf))
                    if msg, err := proxy.Parse(buf); err == nil && msg != nil {
                        r = r.WithContext(proxy.WithMessage(r.Context(), msg))
                    }
                    r.Body = io.NopCloser(bytes.NewReader(buf))
                }
            }

            next.ServeHTTP(ww, r)

            serverID := resolveServerID(r.Context(), serverStore, chi.URLParam(r, "serverName"))
            entry := BuildEntry(r, ww, serverID, start)
            pipeline.Submit(entry)
        })
    }
}
```

### Why middleware ordering matters (and the pivot from the plan)

The original plan placed logging **after** RBAC in the middleware chain:

```go
// ORIGINAL (plan)
r.Use(s.authMiddleware)
r.Use(rbac.Authorize(...))    // short-circuits → 403
r.Use(logging.Middleware(...)) // ← never reached for denied requests
```

`chi` middleware runs in registration order. When RBAC calls `writeJSONError` and returns without calling `next.ServeHTTP`, every middleware registered after it — including logging — never executes. This meant all RBAC-denied requests were silently dropped from the audit log.

**The fix**: move logging before RBAC **and** pre-parse the body inside the logging middleware so RBAC does not need to parse it again.

```go
// FINAL
r.Use(s.authMiddleware)
r.Use(logging.Middleware(...))  // ① pre-parse body, wrap writer, defer Submit
r.Use(rbac.Authorize(...))      // ② reads message from context, may 403
// proxy handler                // ③ only reached if RBAC allows
```

The logging middleware wraps the `ResponseWriter` before calling `next.ServeHTTP(ww, r)`. Even when RBAC short-circuits with a 403, `ww` still captures the status code. After `next.ServeHTTP` returns (regardless of which handler wrote the response), the logging middleware resolves the server ID and submits the entry.

### Body pre-parsing and context handoff

For POST requests, the logging middleware reads the body into a `[]byte` buffer, parses it with `proxy.Parse`, stores the result in context via `proxy.WithMessage`, then **restores** `r.Body` twice: once before calling `proxy.Parse` (unnecessary, since `Parse` takes a `[]byte`, not a reader, but left for correctness), and once after so downstream handlers (RBAC, proxy) can still read it.

RBAC middleware was updated to prefer the context value over re-parsing:

```go
// rbac/middleware.go
if msg := proxy.MessageFromContext(r.Context()); msg != nil {
    action = proxy.Action(msg.Method) // fast path — no body read needed
} else {
    // fallback: read body (e.g. if logging middleware was bypassed)
    buf, _ := io.ReadAll(r.Body)
    ...
}
```

### `resolveServerID`

A helper with a 50 ms timeout on the store lookup. Returns `uuid.Nil` on timeout or error — the log entry still records `server_name`, so the failure is non-fatal. The short timeout prevents a slow DB from blocking the pipeline submission.

### `BuildEntry` (`internal/logging/entry.go`)

```go
func BuildEntry(r *http.Request, ww wrappedWriter, serverID uuid.UUID, startTime time.Time) store.AuditLogEntry {
    identity := auth.IdentityFromContextOrZero(ctx)  // zero if not authenticated
    msg := proxy.MessageFromContext(ctx)              // nil for GET /sse

    entry := store.AuditLogEntry{
        Timestamp:    startTime,
        TraceID:      chimw.GetReqID(ctx),
        SessionID:    identity.SessionID,
        UserID:       identity.UserID,
        UserEmail:    identity.Email,
        ClientIP:     extractClientIP(r),
        ServerID:     serverID,
        ServerName:   chi.URLParam(r, "serverName"),
        Direction:    "response",
        LatencyMS:    int(time.Since(startTime).Milliseconds()),
        RequestSize:  int(r.ContentLength),
        ResponseSize: ww.BytesWritten(),
    }
    // MCPMethod and ToolName populated from msg if non-nil
    // Status, RBACDecision, ErrorCode derived from HTTP status code
}
```

`auth.IdentityFromContextOrZero` was added to `internal/auth/context.go` specifically for this function. When the logging middleware is wired after `authMiddleware`, all reaching requests are authenticated. But since logging sits before RBAC and after auth, the identity is always present. The zero-value fallback guards against future re-ordering.

`extractClientIP` prefers `X-Forwarded-For` over `r.RemoteAddr`. This is only safe because mcpgate is expected to sit behind a trusted reverse proxy (nginx, Traefik, ALB). If deployed edge-facing, this could be spoofed and would need a trusted-proxy list.

## 9. Admin Log API (`internal/admin/api/logs.go`)

All three handlers require the `admin` role (enforced by `RequireRole` applied to the admin group in the router).

### `list` — `GET /api/v1/admin/logs`

Query parameters: `from`, `to` (RFC3339), `user_id`, `server_id`, `method`, `status`, `tool_name`, `search`, `page`, `page_size` (max 200).

Response:
```json
{
  "entries": [...],
  "total": 42,
  "page": 1,
  "pages": 5
}
```

`parseLogParams` validates and parses all query params. Invalid UUIDs, invalid timestamps, and `from > to` all return 400 with a descriptive message.

### `export` — `GET /api/v1/admin/logs/export`

Same filter params as `list`, plus `format=json` (default) or `format=csv`. Sets `Content-Disposition: attachment; filename="mcpgate-logs-YYYYMMDD-HHMMSS.{ext}"`. Streams directly from the DB cursor to the response body — memory usage is independent of result count.

### `stream` — `WS GET /api/v1/admin/logs/stream`

Upgrades the connection to WebSocket using `gorilla/websocket`. The server:

1. Calls `pipeline.Subscribe(connID, 256)` to get a fan-out channel.
2. Starts a read goroutine that accepts JSON `LogFilter` messages from the client and updates a local `filter` variable. When the client disconnects, `cancel()` is called, closing the fan-out channel.
3. Loops over the fan-out channel, skipping entries that do not match `filter`, and writes matching entries as JSON text frames.

The `wsUpgrader` sets `CheckOrigin: func(*http.Request) bool { return true }`. This is safe because the WS endpoint already requires the admin role JWT — an additional origin check would add no security for API clients.

## 10. Bugs Discovered and Fixed During Testing

### Bug 1 — RBAC-denied requests not logged (middleware ordering)

**Symptom**: `TestE2E_AuditLog_RBACDenied_ProducesEntryWithDeniedStatus` timed out waiting for a denied entry that was never written.

**Root cause**: Logging middleware was wired after RBAC. When RBAC wrote a 403 and returned, `next.ServeHTTP` was never called for the logging middleware.

**Fix**: Swap middleware order (logging before RBAC) + pre-parse body in logging middleware + RBAC reads from context.

---

### Bug 2 — Pipeline not running in test environment

**Symptom**: All three E2E audit log tests timed out with no entries in the DB. The pipeline's `writer` goroutine was never started.

**Root cause**: `pipeline.Start(ctx)` was originally called inside `Run()`. E2E tests call `srv.Handler()` and drive requests directly without ever calling `Run()`.

**Fix**: Move `pipeline.Start(context.Background())` and all background goroutine starts into `server.New()`. Add a `Shutdown()` method callable from test cleanup:
```go
func (s *Server) Shutdown() {
    s.bgCancel()    // stop JWKS eviction, session cleanup, WAL replay goroutines
    s.pipeline.Drain()  // flush remaining entries before exit
}
```
Tests register `t.Cleanup(srv.Shutdown)` so the pipeline is drained even on test failure.

---

### Bug 3 — `VerifyHashChain` failed for first batch in fresh database

**Symptom**: `TestE2E_AuditLog_HashChain_Intact` always reported `false` on a fresh test database.

**Root cause**: `VerifyHashChain` looks up the `hash_chain` of the last row before `from`. On a fresh DB this query returns no row, so `prevHash` defaulted to `""`. The pipeline's `HashChain` was seeded with `"test-genesis"`, so the first stored hash was `SHA256("test-genesis" || JSON(entry1))`. Verification recomputed `SHA256("" || JSON(entry1))` — a different hash.

**Fix**: Add a `genesisHash string` parameter to `VerifyHashChain` (both the interface and the implementation). When no prior row is found, `prevHash` is initialised to `genesisHash` instead of `""`. All callers supply the configured seed:
```go
ts.auditStore.VerifyHashChain(ctx, from, to, "test-genesis")
```

---

### Bug 4 — `ID` excluded from hash payload after DB round-trip

**Symptom**: Hash chain verification always failed even with the correct genesis hash.

**Root cause**: `ID` is a `BIGSERIAL` assigned by Postgres after INSERT. At hash-compute time in the pipeline, `entry.ID = 0` (never set). After INSERT, Postgres assigns a real ID (e.g. 1, 2, 3). When `auditVerifyChain` reads rows from DB and recomputes, `entry.ID` is the actual auto-incremented value. Both the pipeline and the verifier serialize the full entry struct to JSON, so the `"ID"` field produces `0` in one and `123` in the other — different JSON strings, different hashes.

**Fix**: Zero `tmp.ID = 0` in both `marshalWithoutHashChain` (in `hashchain.go`) and in `auditVerifyChain` (in `audit_logs.go`), alongside the existing `tmp.HashChain = ""` exclusion:

```go
type shadow store.AuditLogEntry
tmp := shadow(*entry)
tmp.HashChain = ""
tmp.ID = 0   // BIGSERIAL assigned after insert; was 0 at hash-compute time
return json.Marshal(tmp)
```

### Bug 5 — Timestamp timezone mismatch between pipeline and DB

**Symptom**: Hash chain verification still failed after Bug 4 was fixed.

**Root cause**: pgx v5 decodes `TIMESTAMPTZ` using the process's **local timezone**, not UTC. The machine running tests was in `America/New_York` (EDT, `-04:00`). The pipeline normalized the timestamp with `.UTC().Truncate(time.Microsecond)` before hashing, producing `"2026-05-25T16:14:35.978063Z"` in the JSON. After the DB round-trip, pgx returned the same instant as `time.Time` with `loc=Local` (EDT), which `json.Marshal` serialized as `"2026-05-25T16:14:35.978063-04:00"` — a different JSON string.

**Discovery**: A debug test (`TestDebug_HashChain`) was written to log the full JSON used for hashing from both the pipeline and the DB-scanned entry side-by-side, revealing the mismatch immediately.

**Fix**: In `scanAuditEntry`, convert every scanned timestamp to UTC:
```go
e.Timestamp = e.Timestamp.UTC()
```

### Bug 6 — INET column appends `/32` prefix length

**Symptom**: Discovered in the same debug test run as Bug 5.

**Root cause**: Postgres's `INET` type stores IP addresses with a network prefix length (`127.0.0.1` is stored as `127.0.0.1/32`). The `::text` cast in the SELECT returns `"127.0.0.1/32"`. The pipeline entry had `ClientIP = "127.0.0.1"`. Different JSON strings, different hashes.

**Fix**: Strip the CIDR suffix when scanning:
```go
if clientIP != nil {
    e.ClientIP = strings.SplitN(*clientIP, "/", 2)[0]
}
```

### Bug 7 — Pipeline normalization required for Metadata and Timestamp

**Context**: Discovered before the debug test, fixed by adding normalization to the pipeline's `flush()` function.

**`Metadata` (nil → empty map)**: The `store.AuditLogEntry.Metadata` field is `map[string]any`. When not explicitly set, it is `nil`. `json.Marshal(nil map)` produces `null`. Postgres stores `{}` as the `JSONB` default for a NULL insert (via `json.Marshal(nil)` → `"{}"` fallback in BatchInsert), and `json.Unmarshal` of `{}` produces an empty `map[string]any{}`. So `nil` in the pipeline → `map[string]any{}` from DB → different JSON.

**`Timestamp` (nanosecond → microsecond)**: `time.Now()` has nanosecond precision. Postgres `TIMESTAMPTZ` has microsecond precision. Without truncation, the fractional seconds would differ.

**Fix** (in `pipeline.go` `flush()`):
```go
for i := range batch {
    batch[i].Timestamp = batch[i].Timestamp.UTC().Truncate(time.Microsecond)
    if batch[i].Metadata == nil {
        batch[i].Metadata = map[string]any{}
    }
}
```

Normalization runs **before** hash computation in the flush loop, ensuring the hash is computed from values identical to what Postgres will store and return.

## 11. Carry-Over Items

### C1 — stdio Transport Auto-Restart (`internal/proxy/transport/stdio.go`)

**Problem**: If the child process crashed unexpectedly, all in-flight `Send()` calls would block forever on the response channel or the `done` channel, which was never closed again.

**Key additions to `Stdio`**:

```go
closed     atomic.Bool   // true once Close() is called (intentional shutdown)
closeOnce  sync.Once     // prevents double-kill on Close()
// done chan struct{} is now reset per-process, not per-Stdio instance
```

**`readLoop` reset on unexpected exit**:
```go
if t.closed.Load() {
    return  // intentional — Close() handles done
}
// Unexpected exit:
t.procMu.Lock()
oldDone := t.done
t.done = make(chan struct{})  // fresh channel for the next process lifecycle
t.proc = nil
t.stdin = nil
t.procMu.Unlock()
close(oldDone)  // unblocks all Send() callers waiting on this process
```

After `close(oldDone)`, any `Send()` blocked on `<-done` returns `fmt.Errorf("stdio: process exited")`. The caller's next `Send()` triggers `ensureRunning()`, which starts a fresh process under `procMu`.

**`Send()` snapshot under `procMu`**:
```go
t.procMu.Lock()
done := t.done   // snapshot current done before blocking
t.procMu.Unlock()

select {
case resp := <-ch:
case <-ctx.Done():
case <-done:      // safe — snapshot is immutable after procMu is released
}
```

Without the snapshot, `<-t.done` in the select would race against `readLoop` assigning `t.done = make(chan struct{})`. The snapshot under `procMu` ensures `Send()` waits on the `done` channel for the process it already sent the message to, not the next one.

**`Close()` uses `closeOnce`**:
```go
func (t *Stdio) Close() error {
    t.closed.Store(true)
    var err error
    t.closeOnce.Do(func() {
        t.procMu.Lock()
        defer t.procMu.Unlock()
        select {
        case <-t.done:
        default:
            close(t.done)  // safe — guarded by closeOnce
        }
        ...
        if t.proc != nil { err = t.proc.Process.Kill() }
    })
    return err
}
```

`closeOnce` prevents a double-close panic if `Close()` is called twice. The `select` guard on `close(t.done)` handles the race where `readLoop` already closed `t.done` (unexpected exit) before `Close()` was called.

### C2 — JWKS Client Eviction (`internal/auth/jwks/validator.go`)

**Problem**: The `Validator` held a `map[string]*Client` keyed by issuer. The map grew indefinitely because entries were never removed, even for issuers that had not been seen in days.

**Solution**: Wrap each client in a `clientEntry` with an access timestamp, and run a background goroutine that evicts entries unused for `3 × clientTTL`.

```go
type clientEntry struct {
    client   *Client
    lastUsed atomic.Int64  // UnixNano of most recent clientFor() call
}
```

**`clientFor` stamps `lastUsed` on every read** (under the read lock):
```go
if entry, ok := v.clients[issuer]; ok {
    entry.lastUsed.Store(time.Now().UnixNano())
    ...
}
```

**`Start(ctx context.Context)` eviction goroutine**:
```go
func (v *Validator) Start(ctx context.Context) {
    evictInterval := v.clientTTL * 3
    if evictInterval < time.Hour { evictInterval = time.Hour }
    ticker := time.NewTicker(evictInterval)
    defer ticker.Stop()
    for {
        select {
        case <-ticker.C: v.evict()
        case <-ctx.Done(): return
        }
    }
}
```

The minimum eviction interval is 1 hour, regardless of `clientTTL`, to avoid thrashing for very short TTLs in tests. `evict()` acquires the write lock and deletes entries whose `lastUsed` is older than `now - 3×clientTTL`.

`Start` is called from `server.New()` as `go jwksValidator.Start(bgCtx)`, so it stops when `bgCancel()` is called in `Shutdown()`.

### C3 — Session Cleanup Goroutine

Added to `server.New()`:
```go
go func() {
    ticker := time.NewTicker(24 * time.Hour)
    defer ticker.Stop()
    for {
        select {
        case <-ticker.C:
            n, err := sessionStore.DeleteExpired(bgCtx)
            if err != nil {
                logger.Warn("session cleanup failed", "err", err)
            } else {
                logger.Info("session cleanup", "deleted", n)
            }
        case <-bgCtx.Done():
            return
        }
    }
}()
```

`DeleteExpired` issues `DELETE FROM sessions WHERE expires_at < now()` and returns `RowsAffected`. It runs once per day, using `bgCtx` so it stops cleanly on shutdown.

## 15. Key Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | Single writer goroutine for hash chain | The hash of entry N depends on the hash of entry N-1. Fan-out to multiple writers would require a serial handoff for the chain computation anyway, so a single goroutine is simpler and provably correct. |
| D2 | `logging.Sink` and `sinks.Sink` are duplicate interfaces | Avoids import cycle. Structural typing means both `PostgresSink` and `WALSink` satisfy `logging.Sink` without any extra declaration. |
| D3 | `VerifyHashChain` signature includes `genesisHash` | The verifier cannot know the genesis seed at construction time; passing it as a call-site argument makes the contract explicit. Callers must supply the same seed that was configured at startup. |
| D4 | `pipeline.Start(context.Background())` not `bgCtx` | Prevents the writer goroutine from stopping before `Drain()` is called during shutdown, which would drop buffered entries. The writer goroutine's lifecycle is controlled by the `done` channel, not a context. |
| D5 | Normalization before hashing (not on insert) | Normalizing in `flush()` means the hash is computed from values that survive a Postgres round-trip. Normalizing on scan (for verification) would also work, but is harder to reason about and would hide Postgres encoding behavior from the reader. |
| D6 | Logging middleware placed before RBAC | The only way to capture 403 responses from RBAC is to be upstream of it. Body pre-parsing in the logging middleware eliminates the double-parse cost. |
| D7 | `auditVerifyChain` inlined in `audit_logs.go` | Avoids `store/postgres` → `logging` → `store` import cycle. The duplication is contained to ~15 lines and both copies are covered by tests. |
| D8 | `IdentityFromContextOrZero` instead of `MustIdentity` | Logging middleware can in theory be reached before auth runs (or on auth failures if middleware order changes in future). Zero identity produces an audit entry with empty email/UUID rather than a panic. |
