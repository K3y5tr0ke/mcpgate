## 2. Plan Reconciliations

The `stage-9-plan.md` design was sound, but three of its assumptions did not match the code and were corrected before implementation:

### 2.1 `useMetricsTimeseries` already sent a `bucket` param
The plan assumed the hook needed a `window` param added and proposed a `(window, server)` signature. In reality the hook was already `(window = '1h', bucket = '5m')` sending `?window=…&bucket=…`, while the **backend ignored all query params** and always returned 60 fixed buckets.

**Decision:** make bucket resolution **server-derived and reported back** (`window`/`bucket`/`resolution_secs` in the response), drop the client `bucket` input, and change the hook to `(window, server?)`. A `?bucket=` override is left as a future seam (parse + clamp). See §3.1 and D1.

### 2.2 The JWKS rotate endpoint required cross-cutting wiring
The plan sketched `h.jwksCache.Invalidate(cfg.Issuer)` as if the handler already held a cache reference. It did not: `jwks.Validator` had only a private `evict()`, and the admin router never received the validator. Both had to be added (a new `Invalidate` method + threading the validator through `NewRouter`). See §3.2 and D3.

### 2.3 The `6h` bucket count in the plan was internally inconsistent
The plan's table listed `6h → 360 buckets × 1-minute`, which violates its own "keep responses under ~100 points" rationale. Corrected to `6h → 72 buckets × 5-minute`. The final, locked window table:

| `window` | span | `bucket` | `resolution_secs` | points |
|----------|------|----------|-------------------|--------|
| `1h`  | 60m    | `1m`  | 60   | 60 |
| `6h`  | 360m   | `5m`  | 300  | 72 |
| `24h` | 1440m  | `15m` | 900  | 96 |
| `7d`  | 10080m | `2h`  | 7200 | 84 |

## 3. Track A — Backend

### 3.1 A1 — Metrics timeseries: window + per-server params

**Files:** `internal/metrics/collector.go`, `internal/admin/api/metrics.go`

The metrics middleware already wrote a global per-minute key `metrics:ts:{minute}`. A per-server key was added alongside it (the route param is `serverName`, confirmed in `server.go` and `collector.go`):

```go
// internal/metrics/collector.go — Middleware()
if c.redis != nil {
    minute := time.Now().Unix() / 60
    ctx := r.Context()
    key := fmt.Sprintf("metrics:ts:%d", minute)
    c.redis.Incr(ctx, key)
    c.redis.Expire(ctx, key, 7*24*time.Hour)
    // Per-server bucket for the metrics drilldown. Only written when the
    // request carries a serverName (i.e. inside the /mcp/{serverName} group).
    if server != "" {
        srvKey := fmt.Sprintf("metrics:ts:srv:%s:%d", server, minute)
        c.redis.Incr(ctx, srvKey)
        c.redis.Expire(ctx, srvKey, 7*24*time.Hour)
    }
}
```

The `timeseries` handler was rewritten around a window lookup table. Because the middleware only writes 1-minute keys, buckets larger than 1m are computed by summing the per-minute keys spanning each display bucket in a single Redis pipeline:

```go
var windowSpecs = map[string]windowSpec{
    "1h":  {label: "1h", totalMins: 60, bucketMins: 1},
    "6h":  {label: "6h", totalMins: 360, bucketMins: 5},
    "24h": {label: "24h", totalMins: 1440, bucketMins: 15},
    "7d":  {label: "7d", totalMins: 10080, bucketMins: 120},
}
```

- `?window=` defaults to `1h`; an unknown value → **400**.
- `?server=X` switches the key prefix to `metrics:ts:srv:X:`.
- The response gained `window`, `bucket`, and `resolution_secs`; the `h.redis == nil` single-point fallback was preserved (and only emits the in-process count for the global series, since no per-server counter exists in memory).

**Acceptance verified** by integration tests (§5.1): 60/72/96/84 points and 60/300/900/7200s per window; no-param default → 60×1m; unknown window → 400; per-server series reflects only that server's traffic.

### 3.2 A2 — JWKS key rotation endpoint

**Files:** `internal/auth/jwks/validator.go`, `internal/admin/api/jwks.go`, `internal/admin/api/router.go`, `internal/server/server.go`

A public `Invalidate` was added to the validator (it reuses the existing `mu`/`clients` map; analogous to the private `evict()`):

```go
// internal/auth/jwks/validator.go
func (v *Validator) Invalidate(issuer string) {
    v.mu.Lock()
    defer v.mu.Unlock()
    if _, ok := v.clients[issuer]; ok {
        delete(v.clients, issuer)
        v.logger.Info("jwks: invalidated client cache", "issuer", issuer)
    }
}
```

The validator was threaded through `NewRouter` (now 15 params) → the `Router` struct → the `jwksHandler`, and wired in `server.go` (the validator was already constructed there for the auth middleware). The new handler verifies the remote JWKS is reachable and non-empty **before** evicting the cache; it does not store the fetched keys (the validator re-fetches lazily on the next token validation):

```go
// internal/admin/api/jwks.go — rotate()
keyCount, err := fetchJWKSKeyCount(r.Context(), cfg.JWKSURL) // 502 on unreachable / empty
...
if h.validator != nil { h.validator.Invalidate(cfg.Issuer) }
writeJSON(w, http.StatusOK, map[string]any{"issuer": cfg.Issuer, "key_count": keyCount, "rotated_at": time.Now().UTC()})
```

`fetchJWKSKeyCount` uses `http.NewRequestWithContext` + a 10s-timeout client (avoiding gosec G107 on the convenience `http.Get`). Route: `POST /api/v1/admin/jwks/configs/{id}/rotate`. Returns 200 (`key_count`) / 400 (bad id) / 404 (unknown) / 502 (unreachable or empty key set).

## 10. Key Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | Bucket resolution is server-derived and reported (`window`/`bucket`/`resolution_secs`); client `bucket` input dropped | One endpoint, bounded response (≤96 pts); the UI only has window tabs, so a client bucket had nothing to drive it. A `?bucket=` override seam is left for later. |
| D2 | `6h` corrected to 72×5m (from the plan's 360×1m) | Restores the "~100 points max" invariant the plan stated but violated. |
| D3 | Rotate endpoint verifies the remote JWKS before evicting; does not store keys | Invalidation alone is the contract — the validator re-fetches lazily. Verifying first lets the endpoint return a meaningful `key_count` and 502 on bad upstreams. |
| D4 | `IdpWizard` takes an `onSubmit` callback rather than calling the mutation itself | Keeps the wizard pure and unit-testable; the page owns the mutation. |
| D5 | `KeyValueEditor` is controlled (parent owns value) | Avoids state-sync bugs between component and form. |
| D6 | C6 WebSocket test ships `t.Skip` | Documents intended behaviour as an executable spec; the heartbeat is Sprint 10 work. |
| D7 | jsdom polyfills (`localStorage`/`matchMedia`/`<dialog>`) live in shared `setup.ts` | One place; the existing smoke test never needed them. |
| D8 | Vitest scoped to `src/**`, Playwright owns `tests/e2e/**` | Disjoint ownership so Vitest doesn't collect `@playwright/test` specs. |
| D9 | `collector` unit test uses an embedded-`Cmdable` fake | No new mock-Redis dependency for overriding 2 methods. |
| D10 | Playwright lives only in `test-e2e-playwright` / a CI job, not in `ci` | It needs a running server + seeded admin; the no-server `ci` target must not depend on it. |
| D11 | ESLint added to `test-frontend` (gates ci-fast) | Closes the gap where ESLint was never enforced by any Make target. |
| D12 | `useAuth` client-side expiry check removed rather than reworked | Unused, and expiry is already enforced server-side via the 401→login redirect. |

### 12.2 Audit log API JSON casing — dashboard "Invalid time value" (bug + fix)
**File:** `internal/store/interfaces.go` · **commit `c8ee297`**

**Symptom (reported):** the console was "down" — `/console/dashboard` threw **"Invalid Time Value"** and `/console` looked Not Found.

**Root cause:** `store.AuditLogEntry` carried only `db:` tags, no `json:` tags, so `GET /api/v1/admin/logs` serialised **PascalCase** keys (`Timestamp`, `UserEmail`, `Status`, …) while the console types expect snake_case (`timestamp`, `user_email`, …). The dashboard's `format(new Date(e.timestamp), …)` therefore got `undefined` → `Invalid Date` → date-fns throws and white-screens the page. The prior sprint added `json:` tags to the other domain structs but missed `AuditLogEntry`. It was **latent** — there were zero audit entries to render until the §12.1 smoke run created the first three (the proxied `tools/list` calls).

**Fix:** added snake_case `json:` tags to every `AuditLogEntry` field. Backend-only — the console already expected snake_case. Verified after a server restart: `/logs` returns snake_case keys with a valid `timestamp`; `/console` → 302 → dashboard, `/console/dashboard` & `/console/login` → 200 HTML.

**Caveat (→ S9-D9):** `hashchain.go` marshals a `shadow` of this struct, so the hash-chain input representation changed; entries written before the fix now fail `/logs/verify`. New entries are consistent. Pre-launch, so no migration. Logging unit tests assert chain *consistency* (not literal hashes), so they still pass.
