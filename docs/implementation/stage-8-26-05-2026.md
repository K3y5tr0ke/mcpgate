## 1. Bug Fixes

### 1.1 Users page showed no users — response shape mismatch

**File:** `internal/admin/api/users.go`

**Symptom:** The Users page (`/console/users`) loaded without error but displayed an empty table even though users existed in the database. No network error appeared in the browser — the API returned HTTP 200.

**Root cause:** The `userHandler.list` handler serialised the user slice directly as a bare JSON array:

```go
// before
writeJSON(w, http.StatusOK, users)
// → [{"id":"...","email":"..."}]
```

The frontend `useUsers` query in `web/src/api/queries.ts` expected the same envelope shape used by every other list endpoint (`{ "users": [...], "total": N }`):

```ts
apiFetch<{ users?: User[]; total?: number }>('/users?' + toQS(params))
```

Because the response was an array (not an object), `data.users` was `undefined` and the component fell back to `data?.users ?? []` — an empty array. The table rendered zero rows silently.

**Comparison:** the servers handler (`serverHandler.list`) correctly wraps its response:
```go
writeJSON(w, http.StatusOK, map[string]any{"servers": servers, "total": total})
```
The users handler was inconsistent with this pattern.

**Fix:**

```go
// internal/admin/api/users.go — list handler
// before
users, _, err := h.store.List(r.Context(), store.UserFilter{}, store.Pagination{PageSize: 100})
...
writeJSON(w, http.StatusOK, users)

// after
users, total, err := h.store.List(r.Context(), store.UserFilter{}, store.Pagination{PageSize: 100})
...
writeJSON(w, http.StatusOK, map[string]any{"users": users, "total": total})
```

The `_` discard of the total count was also corrected — the second return value from `store.List` is now surfaced in the response, consistent with the servers and logs endpoints.

**Verification:** after restarting the server, `GET /api/v1/admin/users` returns:
```json
{ "users": [{ "id": "...", "email": "prathiksaisb.2595@gmail.com", "status": "active", ... }], "total": 1 }
```
The Users page populates correctly.

### 1.2 Bootstrap — first JIT-provisioned user has no roles

**Symptom:** After the first successful SAML login, the authenticated user received 403 on all admin API routes. Server logs showed:
```
level=INFO msg="rbac: admin access denied" user=prathiksaisb.2595@gmail.com required_role=admin
```

**Root cause:** SAML JIT provisioning (`jitProvision` in `internal/auth/saml/handlers.go`) creates new users with `status: active` but assigns no roles. The `make seed` command seeds role definitions (`admin`, `developer`, `readonly`) but has no mechanism to associate them with dynamically created users. The first operator to log in via SAML is therefore always roleless.

**Workaround applied:** assigned the `admin` role directly via SQL:
```sql
INSERT INTO user_roles (user_id, role_id, assigned_at)
VALUES (
  'a9e1b9d0-f57f-4f52-a0bc-2ffc6c24e051',  -- user ID from users table
  'bdb35810-eaa6-42e9-861d-829ba2e6f908',  -- admin role ID from roles table
  now()
)
ON CONFLICT DO NOTHING;
```

The user then logged out and back in so the ACS handler re-issued a JWT with `"roles": ["admin"]`.

**Permanent fix (deferred to Sprint 8 implementation):** add a `MCPGATE_BOOTSTRAP_ADMIN_EMAIL` environment variable checked at server startup. If set and a user with that email exists with no roles, automatically assign the `admin` role. Alternatively, extend `make seed` with an `--admin-email` flag. Tracked as a deferred item in `stage-8-plan.md`.

### 1.3 `make setup-dev` / `make dev-frontend` — `npm: command not found` (nvm not loaded)

**Symptom:** Running `make setup-dev` failed at the `dev-frontend` step:
```
cd web && npm run dev
/bin/bash: npm: command not found
make[1]: *** [dev-frontend] Error 127
```

**Root cause:** Make recipes run in a non-interactive shell. nvm is only initialised inside `~/.zshrc` which is never sourced by Make. The same root cause was previously fixed in the pre-push hook (`scripts/pre-push.hook`) but not in the Makefile targets themselves.

**Affected targets:** `build-web`, `dev-frontend` (and transitively `build`, `dev-all`, `setup-dev`, `ci-fast`).

**Fix:** Added an `NVM` variable to the Makefile top-level that sources nvm inline, then prefixed it onto each npm-using recipe:

```makefile
# Makefile — top of file
NVM := export NVM_DIR="$${NVM_DIR:-$$HOME/.nvm}"; [ -s "$$NVM_DIR/nvm.sh" ] && . "$$NVM_DIR/nvm.sh";

# build-web
build-web:
    $(NVM) cd web && npm ci && npm run build

# dev-frontend
dev-frontend:
    $(NVM) cd web && npm run dev
```

Because Make expands `$(NVM)` as a shell snippet followed by a semicolon, the `cd` and `npm` commands that follow run in the same shell with nvm already loaded. Verified: `make build-web` completes successfully (`✓ built in 112ms`).

### 1.4 `make seed` — stub printed "not yet implemented" instead of seeding

**Symptom:** `make setup-dev` printed:
```
seed: not yet implemented — coming in Sprint 1
```

**Root cause:** `cmdSeed` in `cmd/mcpgate/main.go` was a Sprint 0 stub that was never implemented. Default roles (`admin`, `developer`, `readonly`) were seeded by migration `003_rbac_seed.up.sql`, so the stub was harmless until `make seed` became a documented setup step. The local admin account creation (Track E, Sprint 8) will be the first real work this command does.

**Fix:** Updated the stub message to accurately reflect the current state — roles come from migrations, local admin creation is Sprint 8 — so operators understand what the command does (and does not do) today:

```go
fmt.Println("Default roles are seeded by database migrations (make migrate-up).")
fmt.Println("Local admin account creation: coming in Sprint 8.")
```

The full `cmdSeed` implementation (connecting to the database, creating the local admin user, printing credentials) is Track E in the Sprint 8 plan.
