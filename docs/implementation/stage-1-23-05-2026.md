## 1. What Was Implemented

Sprint 1 delivers the core proxy engine: JSON-RPC parsing, all three MCP transport adapters, the server configuration store, the admin REST API skeleton, and the wiring that connects them all to the existing chi server. The binary remains fully runnable with `make dev`.

### 1.1 Store Sentinel Errors (`internal/store/errors.go`)

Three package-level sentinel errors shared by all store implementations:

| Error | Usage |
|-------|-------|
| `ErrNotFound` | Row absent; translates pgx `ErrNoRows` |
| `ErrAlreadyExists` | Unique constraint violation |
| `ErrInvalidInput` | Caller-side validation failure |

Handlers and tests use `errors.Is()` against these sentinels. The postgres layer wraps them via `wrapPgError()` in `servers.go`.

---

### 1.2 JSON-RPC 2.0 Parser (`internal/proxy/jsonrpc.go`)

Minimal parse-only decoder. The raw message body is **never modified** before being forwarded upstream — only the fields the proxy needs are decoded:

```
Message
  JSONRPC  string           (validated == "2.0")
  ID       json.RawMessage  (string, number, or null — preserved as-is)
  Method   string
  Params   json.RawMessage
  Result   json.RawMessage
  Error    *RPCError
```

**Key functions:**

| Function | Description |
|----------|-------------|
| `Parse([]byte) (*Message, error)` | Decode + validate version string |
| `(*Message).IsRequest()` | Has `method` field |
| `(*Message).IsNotification()` | Has `method`, no `id` |
| `(*Message).IsResponse()` | No `method` |
| `(*Message).IDKey() string` | Stable string key for `sync.Map` lookups (empty for notifications) |
| `(*Message).ToolName() string` | Extracts `params.name` for `tools/call` only |
| `Action(method string) string` | Maps MCP method → RBAC action category |
| `ErrorResponse(id, code, message)` | Builds a JSON-RPC error response body |

**`Action()` mapping:**

| MCP Method(s) | RBAC Action |
|---------------|-------------|
| `tools/list`, `resources/list`, `prompts/list` | `list` |
| `tools/call` | `call` |
| `resources/read`, `resources/subscribe`, `prompts/get` | `read` |
| `resources/write` | `write` |
| `logging/setLevel` | `admin` |
| `initialize`, `ping` | `connect` |
| anything else | `unknown` |

**Standard error codes** defined as constants: `CodeParseError` (-32700), `CodeInvalidRequest` (-32600), `CodeMethodNotFound` (-32601), `CodeInvalidParams` (-32602), `CodeInternalError` (-32603).

**Tests** (`internal/proxy/jsonrpc_test.go`): 10 unit tests, all passing.

### 1.3 Transport Layer (`internal/proxy/transport/`)

#### 1.3.1 Transport Interface (`transport.go`)

```go
type Transport interface {
    Send(ctx context.Context, message []byte) ([]byte, error)
    Stream(ctx context.Context, message []byte, messages chan<- []byte) error
    Health(ctx context.Context) HealthStatus
    Close() error
}

type HealthStatus struct {
    Healthy bool
    Latency time.Duration
    Err     error
}
```

All three adapters implement this interface, allowing the proxy handler to work against any transport type uniformly.

#### 1.3.2 HTTP Connection Pool (`pool.go`)

Semaphore-based bounded `*http.Client` wrapper. Concurrency is bounded by a buffered channel acting as a counting semaphore. Key properties:

- `Pool.Do(ctx, req)` — blocks until a slot is available or ctx is cancelled
- `PoolMetrics` — three `atomic.Int64` counters: `Active`, `Waiting`, `Total` (available for Prometheus scraping in Sprint 10)
- `PoolConfig.MaxConns` defaults to 50 if zero
- `IdleConnTimeout` defaults to 90s if zero
- The underlying `http.Transport` sets `MaxIdleConnsPerHost` to `MaxConns` to prevent idle connection buildup
- Per-adapter pool instances: each `MCPServer` gets its own pool created at transport-build time

#### 1.3.3 Streamable HTTP Adapter (`streamable.go`)

One POST per JSON-RPC message. Sets `Content-Type: application/json` and `Accept: application/json`. Returns a non-200 HTTP status as an error (upstream-level, not JSON-RPC level). `Health()` sends a `ping` method with a 5-second timeout.

`Stream()` is implemented as a single `Send()` plus a channel push — sufficient for the current request-response model. True server-push streaming over Streamable HTTP will be revisited when the MCP spec evolves.

#### 1.3.4 SSE Adapter (`sse.go`)

Two endpoints:
- `sseEndpoint` — GET, long-lived `text/event-stream`
- `messageEndpoint` — POST, JSON-RPC message delivery

`Send()` POSTs to the message endpoint. If the response `Content-Type` is `text/event-stream`, it reads the first `data:` event; otherwise treats it as a plain JSON response body.

`Stream()` opens a GET against the SSE endpoint and pushes each `data:` event line to the `messages` channel until ctx is cancelled.

#### 1.3.5 stdio Adapter (`stdio.go`)

Spawns a child process and communicates via newline-delimited JSON on stdin/stdout. Designed for MCP servers distributed as CLI tools (e.g., `npx @modelcontextprotocol/server-filesystem`).

**Key design decisions:**

- Process is started **lazily** on first `Send()` call (not at construction time)
- A background `readLoop` goroutine reads stdout continuously and routes each response to the waiting `Send()` caller via a per-ID channel stored in `pending sync.Map`
- `writeMu sync.Mutex` serialises writes to stdin, allowing concurrent `Send()` callers
- `procMu sync.Mutex` guards process lifecycle; `LoadOrStore` on `transports` in the handler prevents duplicate process spawns under concurrent first-request load
- `closeOnce` ensures `Close()` is idempotent
- When the child process exits, `readLoop` closes the `done` channel, unblocking all waiting `Send()` calls with `"stdio: process exited"` error
- Process restart on failure is **not implemented** in Sprint 1 — tracked as TODO

### 1.5 ServerStore Implementation (`internal/store/postgres/servers.go`)

Full pgx/v5 implementation of `store.ServerStore`:

| Method | Notes |
|--------|-------|
| `Create` | `RETURNING id, created_at, updated_at`; populates `server.ID` on success |
| `GetByID` | Single row scan |
| `GetByName` | Single row scan |
| `List` | `ORDER BY name`; returns `nil` (not empty slice) when no rows |
| `Update` | Checks `RowsAffected() == 0` → `ErrNotFound` |
| `Delete` | Checks `RowsAffected() == 0` → `ErrNotFound` |
| `UpdateTools` | Transactional: DELETE all existing tools then batch-upsert new ones |

**pgx v5 UUID scanning** — `pgtype.UUID` is scanned then cast: `uuid.UUID(idPG.Bytes)`. Passing `uuid.UUID` directly to pgx v5 scan causes a type mismatch.

**JSONB columns** (`config`, `health_check`) — marshalled to `[]byte` on write, unmarshalled from `[]byte` on read. pgx v5 does not auto-marshal `map[string]any` into JSONB.

`wrapPgError()` translates `pgx.ErrNoRows` → `store.ErrNotFound` and wraps all other errors with a context prefix.

**Integration tests** (`servers_test.go`, `//go:build integration`): `TestServerStore_CRUD` covers the full create → read → list → update → updateTools → delete cycle. `TestServerStore_NotFound` verifies `ErrNotFound` is returned correctly.

### 1.7 Proxy Handler (`internal/proxy/handler.go`)

The central orchestrator:

```
request → Parse JSON-RPC → resolve server config → resolve/build Transport → Send → return response
```

**Handler struct:**

```go
type Handler struct {
    servers    store.ServerStore
    proxyCfg   config.ProxyConfig
    logger     *slog.Logger
    transports sync.Map          // serverName → transport.Transport
    cacheMu    sync.RWMutex
    cache      map[string]*store.MCPServer
    cacheExp   map[string]time.Time
}
```

**Route handlers:**

| Handler | Route | Description |
|---------|-------|-------------|
| `HandleStreamableHTTP` | `POST /mcp/{serverName}/message` | Full request-response proxy |
| `HandleSSEStream` | `GET /mcp/{serverName}/sse` | SSE event stream (fan-out loop) |
| `HandleSSEMessage` | `POST /mcp/{serverName}/sse` | SSE message injection |

**Server config cache** — 30-second TTL (`serverCacheTTL`). `sync.RWMutex` guards the two maps. This avoids a DB round-trip on every proxied request. Cache is invalidated implicitly on TTL expiry; explicit invalidation on `PUT /servers/{id}` is a Sprint 2+ concern.

**Transport factory** — `buildTransport()` switches on `server.Transport`:

| Value | Adapter | Required config keys |
|-------|---------|----------------------|
| `streamable_http` | `transport.StreamableHTTP` | `config.endpoint` |
| `sse` | `transport.SSE` | `config.sse_endpoint`, `config.message_endpoint` |
| `stdio` | `transport.Stdio` | `config.command`; optional `config.args[]` |

`LoadOrStore` on `transports sync.Map` makes first-request transport creation race-safe: if two goroutines race to create the first transport for a server, the loser's instance is immediately `Close()`d.

**Request body** is limited to `cfg.Proxy.MaxRequestSize` (defaulting to 4 MiB) via `io.LimitReader`.

**Error responses** always use HTTP 200 with a JSON-RPC error object — correct per JSON-RPC 2.0 spec.

### 1.8 Admin REST API (`internal/admin/api/`)

#### `router.go`

`Router` wraps `store.ServerStore` and `*slog.Logger`. `Handler()` returns a chi sub-router mounted at `/api/v1/admin`:

```
GET    /api/v1/admin/servers          → list all servers
POST   /api/v1/admin/servers          → create server
GET    /api/v1/admin/servers/{id}     → get server by UUID
PUT    /api/v1/admin/servers/{id}     → update server
DELETE /api/v1/admin/servers/{id}     → delete server
GET    /api/v1/admin/users            → 501 Not Implemented (Sprint 2)
GET    /api/v1/admin/roles            → 501 Not Implemented (Sprint 4)
GET    /api/v1/admin/logs             → 501 Not Implemented (Sprint 6)
GET    /api/v1/admin/metrics          → 501 Not Implemented (Sprint 10)
```

`writeJSON` and `writeJSONError` helpers are defined in `router.go` and used by all handlers in the package.

#### `servers.go`

`serverHandler` implements all five CRUD operations. All handlers:
- Return `400` for malformed JSON or missing required fields (`name`, `transport`)
- Return `404` via `errors.Is(err, store.ErrNotFound)`
- Return `409` via `errors.Is(err, store.ErrAlreadyExists)` on create
- Return `201 Created` with the populated `*MCPServer` (including DB-assigned `id`) on create
- Return `204 No Content` on delete

### 1.9 Server Wiring (`internal/server/server.go`)

`New()` now creates the store and handler chain before building the router:

```go
serverStore  := pgstore.NewServerStore(db)
proxyHandler := proxy.NewHandler(cfg.Proxy, serverStore, logger)
adminRouter  := api.NewRouter(serverStore, logger)
```

Route groups added to `buildRouter()`:

```
/mcp/{serverName}/message   POST  → proxyHandler.HandleStreamableHTTP
/mcp/{serverName}/sse       GET   → proxyHandler.HandleSSEStream
/mcp/{serverName}/sse       POST  → proxyHandler.HandleSSEMessage
/api/v1/admin               Mount → adminRouter.Handler()
```

Auth middleware (`SAML`, `JWT`) and RBAC middleware (`Casbin`) are **not yet applied** — they will wrap the `/mcp/` and `/api/v1/admin` route groups in Sprints 2 and 4 respectively. Currently all proxy and admin routes are unauthenticated.

## 2. Decisions

### D1 — `fs.FS` parameter instead of importing `postgres` in `testutil`

**Decision:** `testutil.NewPostgresPool` accepts an `fs.FS` parameter rather than importing `internal/store/postgres` directly.

**Rationale:** `internal/store/postgres/servers_test.go` (package `postgres_test`) imports `testutil`. If `testutil` imported `internal/store/postgres`, Go's import graph would have `postgres_test` → `testutil` → `postgres`, which is fine at the package level, but importing the package under test from a helper creates a tight coupling and can cause unexpected recompilation. Accepting `fs.FS` keeps `testutil` decoupled from any concrete store package. Callers pass `postgres.Migrations` explicitly.

### D2 — Lazy process start for stdio transport

**Decision:** The stdio child process is not spawned at `NewStdio()` time; it starts on the first `Send()` call.

**Rationale:** `NewStdio` may be called speculatively during transport-factory setup. Starting the process only when actually needed avoids orphan processes when a transport is created but the server is then disabled or replaced before any traffic arrives.

### D3 — `LoadOrStore` for transport cache race safety

**Decision:** `transports sync.Map` uses `LoadOrStore` then `Close()` on the losing transport rather than a `sync.Mutex`-protected `if _, ok := h.transports.Load(key); !ok`.

**Rationale:** `sync.Map.LoadOrStore` is lock-free for the common case (already present). For the first-request race, the cost of instantiating and immediately discarding one transport is negligible and avoids holding a mutex during transport construction (which may do network I/O for health checks in future).

### D4 — 30-second server config cache in handler

**Decision:** `Handler` caches `MCPServer` rows for 30 seconds (`serverCacheTTL`).

**Rationale:** The proxy is on the hot path for every MCP request. Without a cache, each message would require a DB round-trip to resolve the server config. 30 seconds is long enough to absorb burst traffic, short enough that config changes (e.g., disabling a server) propagate within a reasonable time. An explicit cache invalidation hook will be added in Sprint 2 when the admin API gains an auth layer.

### D5 — HTTP 200 for all JSON-RPC error responses

**Decision:** `writeError()` always writes HTTP 200 with a JSON-RPC error object in the body.

**Rationale:** JSON-RPC 2.0 specifies that error responses are not HTTP-level errors. MCP clients parse the JSON body, not the HTTP status code. Using 4xx/5xx would break spec-compliant clients.

### D6 — One pool per server, not a shared global pool

**Decision:** Each `MCPServer` transport gets its own `transport.Pool` instance, sized by `cfg.Proxy.ConnectionPool.MaxPerServer`.

**Rationale:** A shared global pool could allow a single misbehaving server to exhaust connections for all others. Per-server isolation bounds the blast radius. The tradeoff is slightly higher idle memory usage, acceptable at the expected server counts (tens, not thousands).

### D7 — `UpdateTools` is fully transactional: DELETE then INSERT

**Decision:** `UpdateTools` deletes all existing tools for the server in a transaction, then inserts the new set.

**Rationale:** Diffing old vs new tool lists in application code is error-prone and not meaningfully faster at expected tool counts (< 100 per server). The DELETE + INSERT approach is simpler and gives atomic visibility: readers never see a partial update. `ON CONFLICT DO UPDATE` is used on the insert to handle any duplicate within the provided slice.

### D8 — Admin placeholder routes return 501

**Decision:** `/api/v1/admin/users`, `/roles`, `/logs`, `/metrics` return `501 Not Implemented` immediately.

**Rationale:** Clients and smoke tests can hit these endpoints and get a meaningful status code rather than a 404 (which would imply the route doesn't exist at all). It also reserves the URL space correctly from the start.

## 3. Modifications to Original Plan

### 3.1 `testutil/db.go` signature changed

The original plan proposed `NewPostgresPool(t *testing.T) *pgxpool.Pool` with the migrations path hardcoded. The implemented signature is `NewPostgresPool(t *testing.T, migrations fs.FS) *pgxpool.Pool`. See Decision D1.

### 3.2 `transport.Stream()` for Streamable HTTP is simplified

The architecture blueprint described full server-sent-events multiplexing for the Streamable HTTP transport. The current `StreamableHTTP.Stream()` does a single `Send()` and writes one message to the channel. Full multiplexed streaming (long-poll, chunked body) is deferred to Sprint 5 when the SSE/streaming upgrade path is better defined in the MCP spec.

### 3.3 `HandleSSEStream` does not connect to upstream SSE

The current `GET /mcp/{serverName}/sse` handler establishes a client-facing SSE stream but does not yet open the corresponding SSE connection to the upstream server. The goroutine simply waits for ctx cancellation. Full bidirectional SSE proxying is Sprint 5 scope.

### 3.4 No per-request circuit breaker

The `config.CircuitBreakerConfig` struct exists from Sprint 0, but the circuit breaker is not wired into the transport layer in Sprint 1. All errors from `tr.Send()` are returned directly to the caller with `CodeInternalError`. Circuit breaking is Sprint 5 scope.

### 3.5 Transport cache is never invalidated (hot reload absent)

Transport instances are stored in `sync.Map` indefinitely. If a server's config changes (e.g., endpoint URL updated via `PUT /servers/{id}`), the old transport continues to be used until the process restarts. Cache invalidation tied to admin API writes is Sprint 2 scope.
